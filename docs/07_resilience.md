# 07. Устойчивость и fallback внутри продукта

Ground truth по поведению при сбоях. Схемы: **F1** (сбой источника → политика факта), **F2** (выдача: деньги ровно один раз), **S0** (инъекция отказов из песочницы).
Fallback здесь — **поведение продукта**, а не только ретраи: что происходит с заявкой, что видит клиент, что видит аналитик, что пишется в аудит.

## 1. Принципы
1. **Заявка никогда не зависает.** У каждого нестационарного состояния есть срок и выход по state machine.
2. **Прогресс не теряется.** Каждая команда — одна транзакция «заявка + события + задачи» [P1]; каждый шаг конвейера — чекпоинт; повтор шага идемпотентен.
3. **Деградируем по правилам, а не падаем.** Что делать, если факт неизвестен или устарел, записано в базе знаний (политика факта, 04 §5) и покрыто тестами.
4. **Честный статус.** Клиент видит, какой шаг ждёт какой источник и до какого срока; кабинет читает снапшоты и работает при любых сбоях внешних систем.
5. **Критичное — только на свежих данных.** Подпись и выдача не проходят на устаревших МЧД, ЕГРЮЛ и юр. проверках.
6. **Деньги ровно один раз.** Ключ идемпотентности, сверка статуса перед повтором, никаких ретраев на бизнес-отказы [P3].
7. **Мусор — не данные.** Битый ответ БКИ не означает «долгов нет»; это «источник недоступен».
8. **Любой отказ моделируется на лету.** Песочница меняет поведение WireMock через admin API, ни один контейнер не перезапускается [P18].

## 2. Классификация сбоев
| Класс | Пример | Как моделируем в WireMock |
|---|---|---|
| Задержка | ответ за 1,5 с вместо 0,2 с | `delayDistribution: {type: lognormal, median, sigma}` или `uniform` |
| Таймаут | ответа нет дольше таймаута клиента | `fixedDelayMilliseconds` больше таймаута |
| Транспорт | обрыв, пустой ответ | `fault: CONNECTION_RESET_BY_PEER`, `EMPTY_RESPONSE` |
| Протокол | мусор вместо JSON | `fault: MALFORMED_RESPONSE_CHUNK`, `RANDOM_DATA_THEN_CLOSE` |
| Сервер | 500, 502, 503 с `Retry-After` | `status` + `headers` |
| Ограничение | 429 | `status: 429` + `Retry-After` |
| Семантика | 404 «нет записи», дрейф схемы (200 без обязательного поля), противоречие источников, устаревшие данные | тело ответа из шаблона с изменениями |
| Флаппинг | две ошибки, потом успех | Scenarios: `requiredScenarioState` → `newScenarioState` [P18] |
| Частичный | падает только для одного ИНН | матчинг по пути или телу (`matchesJsonPath`) |
| Наш сбой | воркер остановлен или упал | пауза воркера из песочницы; `docker compose restart worker` |
| Наша БД | PostgreSQL недоступен | API отвечает 503 (Problem Details), фронт показывает баннер; в демо не моделируем — в проде HA |

## 3. Механизмы
| Механизм | Параметры (демо, конфиг) | Где | Ссылка |
|---|---|---|---|
| Таймауты на каждый вызов | connect 1 с, read 3 с (БКИ — 5 с) | адаптеры worker | [P4] |
| Ретраи с экспоненциальным backoff и полным jitter, **в одном слое** | до 3 попыток, база 0,5 с, потолок 4 с; только идемпотентные вызовы; уважаем `Retry-After` | адаптеры worker | [P4] |
| Circuit breaker на источник | 5 отказов подряд → OPEN на 30 с → HALF_OPEN: одна проба; состояние в `kv` | адаптеры worker | [P5] |
| Bulkhead | не больше 4 одновременных вызовов на источник | адаптеры worker | [P6] |
| Снапшоты с TTL и stale-while-revalidate | TTL по источнику (09 §2); устаревший снапшот отдаём, обновляем в фоне | integrations → API | [P7] |
| Политика факта | `STALE_OK`, `WAIT`, `ASSUME_STRICT`, `ASK`, `PROVISIONAL`, `BLOCK`, `MANUAL`, `IGNORE` | база знаний движка | 04 §5 |
| Чекпоинты шагов и аренда | `jobs.lease_until`; просроченная аренда → шаг перезапускается | worker | — |
| Дедлайны и SLO | CHECKING: цель 60 с; ожидание источника — до 15 мин (демо), затем MANUAL | worker (sweeper) | §8 |
| Outbox + `SKIP LOCKED` | обработчики идемпотентны, доставка «хотя бы раз» | все модули | [P1] |
| Idempotency-Key на командах | подать, принять, подписать, выдать | API, АБС | [P3] |
| SSE с `Last-Event-ID` + polling | клиент восстанавливает состояние после разрыва | API | — |
| Пересмотр после восстановления | breaker закрылся → догоняем шаги в `RETRY_WAIT` и предварительные оферты; если исход изменился — `RECHECK` и дифф клиенту | worker | — |

## 4. Политики фактов (что продукт делает, если источник недоступен)
| Факт (источник) | Где нужен | TTL | До подписи | Подпись и выдача |
|---|---|---|---|---|
| ЕИО, режим, дисквалификация, недостоверность (ЕГРЮЛ, реестр дисквал.) | права, стоп-факторы | 24 ч | `STALE_OK` ≤ 7 дн. + `DEGRADED_DATA`; нет снапшота → `WAIT` | `BLOCK`: только свежие (≤ 1 ч) → `WAIT` → дедлайн → `MANUAL` |
| Участники, ОПФ, ОКВЭД (ЕГРЮЛ) | корп. одобрения, подбор | 24 ч | `STALE_OK` ≤ 30 дн. | — |
| Активы (ГИР БО `current1600`) | порог 25% | 30 дн. | нет отчётности (404) → `ASSUME_STRICT` (сделка крупная) или `ASK` (промежуточный баланс) | — |
| Недоимка, МСП, режим (ФНС) | стоп-фактор, продукты | 7–30 дн. | `STALE_OK` | — |
| Кредитная история (БКИ) | риск, банкротство | на заявку | `WAIT` → дедлайн: сумма ≤ `provisional_max` → `PROVISIONAL`, иначе `MANUAL` | предварительная оферта не подписывается без КИ |
| МЧД (реестр МЧД) | подпись представителя | 1 ч | — | `BLOCK`: непроверенную доверенность не принимаем → задача ЕИО или ждать |
| Банкротство, суды, перечни (юр. проверки) | стоп-факторы | 1 дн. | `STALE_OK` | `BLOCK` перед выдачей → `WAIT` → дедлайн → `MANUAL` |
| Транзакции (банк) | предодобрение, K1, лимит овердрафта | 1 ч | `STALE_OK` ≤ 24 ч с датой; нет данных → K1 и предодобрение скрыты, конвейер `WAIT` | — |
| Доступы ДБО, устав (банк) | `prepare`, согласие по уставу | 1 ч | `STALE_OK` ≤ 24 ч | — |
| АБС | выдача | — | — | идемпотентный повтор + сверка статуса → дедлайн → `MANUAL` (`DISBURSE_ERROR`), F2 |
| ЕИС | K5 | 1 дн. | `IGNORE` | — |
| LLM (опционально) | пересказ | — | `IGNORE` → шаблоны | — |

## 5. Сбой на уровне транспорта → политика факта
| Что пришло | Как распознаём | Ретраи | Breaker | Итог |
|---|---|---|---|---|
| Ответ медленнее обычного, но в таймаут укладывается | время ответа | — | нет | ок; метрика p95 |
| Таймаут | `httpx.TimeoutException` | да (для POST — только с Idempotency-Key) | +1 | после ретраев → политика факта |
| 500 / 502 / 503 | статус | да, с учётом `Retry-After` | +1 | то же |
| 429 | статус | да, с `Retry-After` | нет | замедляемся, не авария |
| Обрыв, пустой ответ | транспортная ошибка | да | +1 | то же |
| Мусор (битый ответ) | ошибка разбора | 1 раз | +1 | «источник недоступен», **не «данных нет»** |
| 200, но схема не та | валидация Pydantic по контракту | нет | +1 | как недоступность + флаг «нарушен контракт», для критичных шагов `MANUAL` |
| 404 «нет записи» | статус | нет | нет | семантика «не найдено»: нет БФО → `ASSUME_STRICT`/`ASK`; нет МЧД в реестре → доверенность не подтверждена |
| Противоречие источников | правило согласованности | нет | нет | `MANUAL` с причиной `DATA_CONFLICT` |
| Breaker OPEN | состояние в БД | не вызываем | — | сразу политика факта, без ожидания таймаутов |

## 7. Отказы на лету без даунтайма (WireMock)
Песочница (08) пишет в WireMock admin API стабы отказов с **приоритетом 1** (персона — 3, штатные стабы — 5; штатный стаб — один на ручку, тело выбирается по ИНН, 06 §12), поэтому отказ перекрывает штатный ответ, пока его не удалят.
Скоуп — все ИНН или один (матчинг по пути или телу). Длительность — до отмены, на N вызовов (цепочка состояний Scenarios) или на M минут (стаб удаляет sweeper песочницы).
Снять: `DELETE /__admin/mappings/{id}`; сбросить состояния: `POST /__admin/scenarios/reset`; вернуть штатный мир: `POST /__admin/mappings/reset`. Контейнеры не перезапускаются.

```json
{ "priority": 1,
  "request":  { "method": "POST", "urlPath": "/bki/v1/credit-reports",
                "bodyPatterns": [ { "matchesJsonPath": "$[?(@.subject.inn == '7700000001')]" } ] },
  "response": { "status": 200, "fixedDelayMilliseconds": 10000 },
  "metadata": { "createdBy": "sandbox", "fault": "BKI_TIMEOUT" } }
```
```json
{ "priority": 1, "request": { "method": "GET", "urlPathPattern": "/egrul/v1/legal-entities/.*" },
  "response": { "fault": "CONNECTION_RESET_BY_PEER" }, "metadata": { "createdBy": "sandbox", "fault": "EGRUL_RESET" } }
```
Флаппинг (две ошибки, потом штатный ответ):
```json
[ { "priority": 1, "scenarioName": "fns-flap", "requiredScenarioState": "Started", "newScenarioState": "fail-2",
    "request": { "method": "GET", "urlPathPattern": "/fns/v1/.*" }, "response": { "status": 503, "headers": { "Retry-After": "1" } } },
  { "priority": 1, "scenarioName": "fns-flap", "requiredScenarioState": "fail-2", "newScenarioState": "recovered",
    "request": { "method": "GET", "urlPathPattern": "/fns/v1/.*" }, "response": { "status": 503 } } ]
```
В состоянии `recovered` стабы отказа не совпадают, и отвечает штатный стаб.
Обрыв после списания (N7): `POST /abs/v1/loans/{id}/disburse` в состоянии `Started` → `fault: CONNECTION_RESET_BY_PEER`, `newScenarioState: disbursed`;
в состоянии `disbursed` `GET /abs/v1/loans/{id}` и повторный `POST` с тем же ключом → `200 {"status": "DISBURSED"}`.
Глобальная задержка всех ответов — `POST /__admin/settings {"fixedDelay": 500}`. Журнал запросов `GET /__admin/requests` показывает, какие вызовы реально ушли (доказательство для демо).
Наш собственный сбой — `POST /api/v1/sandbox/worker/pause` (флаг в БД, воркер перестаёт брать задачи; API работает).

## 9. Наблюдаемость
- Таймлайн заявки: шаги, попытки, следующая попытка, флаги — то же видит аналитик.
- Состояние breaker по источникам (`kv`) → баннеры в кабинете, панель в песочнице, досье аналитика.
- Логи JSON с `X-Request-Id` / trace context [P21] от API через очередь задач и воркер до WireMock; журнал запросов WireMock.
- Метрики (Should): время решения, доля STP, срабатывания политик фактов по типам, состояние breaker, повторы выдачи.

## 10. Тесты отказов
- **Набор N1–N17** на pytest: тест ставит стабы через admin API, запускает конвейер, проверяет статус, флаги, причины, аудит и текст для клиента; гоняется в CI в профиле `test`.
- **Идемпотентность:** двойная подача, двойное принятие, повтор выдачи — один результат.
- **Контракты:** адаптеры против образцов реальных форматов (ЕГРЮЛ 4.06, XSD ФНС, ЦБ v3.4); дрейф схемы распознаётся.
- **State machine:** все разрешённые и запрещённые переходы, таймеры, пересмотр.
