# 03. Умные механизмы

Умность = закрытая работа клиента (JTBD) + **алгоритм над данными**, детерминированный и объяснимый. LLM в пути решения нет: недетерминированность,
объяснимость (Кодекс этики ИИ ЦБ, `refs/cbr/`), «необъяснимое поведение — баг». ML — порт на будущее. Ссылки вида [P4], [L18], [M1] — в `10_sources.md`.

Формат карточки: **зачем** → **как работает** → **где в пути** → **если сломалось** → **как показать** → **откуда идея** → приоритет.
Коды: U — базовые механики, K — проактивный доп. слой, X — экспертная система и объяснимость, B — эффективность банка.

---

## A. Данные вместо анкеты

### U3 + X1. Предзаполнение с происхождением · Must
- **Зачем:** повторный ввод — главная боль кейса; клиенту важно понимать, откуда банк это знает.
- **Как:** каждый факт хранится с `source`, `fetchedAt`, `ttl`, `snapshotId` (provenance). Заявка собирается из фактов, клиент подтверждает и дополняет только недостающее.
  Экран «Что банк знает о компании»: факты, источники, даты, кто вправе действовать и почему.
- **Где:** DRAFT, главная, досье аналитика.
- **Если сломалось:** источник недоступен → показываем последний снапшот с датой и флагом `DEGRADED_DATA` (политика `STALE_OK`, 07 §4).
- **Показать:** открыть заявку — поля уже заполнены, у каждого всплывает «ЕГРЮЛ, 21.10 14:02».
- **Откуда:** data lineage в банковских DWH; принцип «спроси один раз».

### U9. Реестр согласий · Should
- **Зачем:** не переспрашивать согласие на БКИ. **Как:** `Consent(subject, purpose, givenAt, validUntil)`; для МСП и поручителя по сделке с МСП — 1 год [L7].
  Перед запросом в БКИ проверяем действующее согласие; нет — один экран согласия. **Где:** подача, поручитель (R7).

### X7. Живые данные · Must
- **Зачем:** банк не *назначает* директора, а *узнаёт* его из ЕГРЮЛ; мир меняется во время процесса.
- **Как:** событие `registry.changed` (новый снапшот, другой hash) → пересчёт прав и требований **только по затронутым** компаниям и заявкам → задачи нужным людям, SSE в открытые вкладки.
  Если изменение влияет на решение (стоп-фактор после оферты) — пересмотр `RECHECK`.
- **Где:** любой этап до выдачи. **Показать:** R12 — в песочнице «сменить директора», у прежнего пропадает кнопка «Подписать», новому приходит задача.

## B. Решаем как эксперт, объясняем как человек

### X2. Экспертная система: правила как данные · Must
- **Зачем:** кредитная логика и юридические corner cases должны быть объяснимы, версионируемы и тестируемы без релиза.
- **Как:** факты → **прямой вывод** до неподвижной точки (производные факты: «крупная сделка», «нужны оба директора», «требуется согласие ОСУ»)
  → **таблицы решений** с политиками срабатывания как в DMN (лимит = `COLLECT MIN` по капам, ставка = `UNIQUE`) [P10] → исход по приоритету
  → трасса. Неизвестные факты — трёхзначная логика с политикой на случай «не знаю». Полностью — `04_decision_engine.md`.
- **Где:** конвейер (commit), предодобрение, K2, K3, VOI (simulate). Страница E1.
- **Если сломалось:** нет движка — нет решения; поэтому он чистый (без IO), покрыт табличными тестами и golden-файлами по каждому сценарию.
- **Откуда:** экспертные системы с прямым выводом, Rete [P11]; DMN decision tables [P10]; бизнес-правила в кредитных движках.

### X3. Юридический навигатор · Must
- **Зачем:** «кто у нас вправе подписать и какие одобрения нужны» — самое непонятное для клиента и самое рискованное для банка.
- **Как:** правила базы знаний над сущностями (ЕИО и режим, участники и доли, МЧД и статус, ДБО, дисквалификация, недостоверность, устав, ОПФ, активы по ГИР БО)
  с нормой в каждом правиле: 14-ФЗ ст. 40, 45, 46; 208-ФЗ ст. 78–79; ГК ст. 53, 67.1, 174, 185.1; КоАП ст. 3.11 (`05_legal.md`).
  Выход: `can_view / can_prepare / can_sign` для пары «человек × компания», список подписантов и требуемых решений органов.
- **Где:** переключатель компаний, кнопки действий, задачи, дозапрос корпоративных решений. Страницы R1–R13.
- **Показать:** R2 — «согласие участников не требуется: единственный участник — он же директор (14-ФЗ ст. 46 п. 7)»; R6 — «подпись засчитана, ждём второго директора (ГК ст. 53 п. 1)».

### X4. «Почему так?» · Must
- **Как:** трасса решения (сработавшие правила, входные факты, нормы) → reason codes → шаблоны текста. Разложение ставки: КС [M1] + отраслевой спред [M4] + спред за риск.
  Панель доступна на каждом экране; аналитик видит ту же трассу в досье.
- **Откуда:** требование объяснимости автоматизированных решений; практика reason codes в кредитовании.

### X8. «Без сюрпризов» · Must
- **Как:** один движок в двух режимах: `simulate` (предодобрение, K2, K3, VOI) и `commit` (решение по заявке). Если итог commit отличается от показанного заранее,
  клиент видит дифф и причину («после проверки КИ лимит 1,8 млн вместо 2,0: просрочка 35 дней по кредиту в другом банке»).

## C. Спрашиваем только то, что меняет решение

### X5. Дозапрос по ценности информации (VOI) · Should
- **Зачем:** лишние документы — главная боль МСБ после повторного ввода; аналитику тоже не нужны бумаги «на всякий случай».
- **Как:** для каждого неизвестного факта движок в режиме simulate считает исход при лучшем и худшем значении из допустимого диапазона.
  Если исход одинаковый — **не спрашиваем**. Если разный — спрашиваем, сортируя по влиянию и трудоёмкости (04 §6).
- **Безопасные умолчания:** если спрашивать нельзя или клиент не может ответить, правило берёт **строгий вариант** и объясняет это
  («отчётности в ГИР БО нет → считаем сделку крупной → нужно решение участников»; клиент может вместо этого загрузить промежуточный баланс).
- **Где:** конвейер, экран дозапроса (U5, D3). **Откуда:** теория ценности информации [P13]; progressive profiling.

## D. Отказ — не тупик, оферта — выбор

### K3. Путь к одобрению (контрфакты) · Must
- **Как:** набор рычагов, которые клиент реально может изменить: сумма ↓, срок ↑, поручитель, залог, погасить недоимку, перевести обороты в банк, подождать N месяцев.
  Перебор комбинаций до двух рычагов, каждая — через `simulate`; оставляем улучшающие исход, ранжируем по эффекту и «цене» для клиента, показываем 1–3 (04 §7).
  Неустранимое (банкротство, ликвидация) — честно: изменить нельзя.
- **Где:** экран отказа (D4) и контрпредложения (D2). Выбранное действие → «подать с изменениями» = клон заявки, предзаполненный.
- **Откуда:** контрфактические объяснения [P12]; Nav «next best option».

### X6. Оферта из вариантов · Should
- **Как:** оптимизатор контрпредложения (04 §8) возвращает основной вариант и до двух альтернатив внутри политики:
  «5 млн с поручительством собственника» или «3,2 млн без поручительства»; «2 млн на 12 мес.» или «2 млн на 18 мес. с меньшим платежом».
- **Зачем:** клиент выбирает сам, конверсия выше, отказ превращается в выбор. Вид оферты остаётся одним статусом OFFERED.

## E. Банк приходит раньше потребности (доп. слой K, страница K0)
Каждый K за фича-флагом `FEATURE_K1…K5`; выключение не ломает основу; новых статусов K не создают; `insights` зависит от основы, обратная зависимость запрещена (import-linter).

### K1. Радар кассового разрыва · Must
- **Как (детерминированно, объяснимо):**
  1. **Регулярные потоки:** транзакции за 12 мес. группируем по (контрагент, категория, направление); поток считаем регулярным, если ≥ 3 операции с устойчивым интервалом
     (неделя, две недели, полмесяца, месяц) — как статус `MATURE` у Plaid [P16]. Ожидаемая дата — по медиане интервала, сумма — медиана трёх последних.
  2. **Календарь обязательств:** НДС — равными долями до 28-го трёх месяцев после квартала, взносы — до 28-го, НДФЛ — 28-го и 5-го [L18]; зарплата — не реже чем каждые полмесяца [L19];
     платежи по нашим кредитам и по данным БКИ (`AvgMonthPaymentSum`).
  3. **Нерегулярные поступления** — медиана по тем же дням прошлых месяцев; разброс остатков даёт коридор P10–P90.
  4. **Прогноз остатка** по дням на 30 дней; разрыв — первая дата, где консервативный прогноз (P10) ниже буфера [параметр].
  5. **Объяснение:** что приходится на день разрыва (налоги 210 тыс., ЗП 480 тыс.) и чего не хватает.
- **Выход:** `insight.signal {CASH_GAP, date, amount, confidence, drivers[]}` → K2. Разрыва нет — «на 30 дней всё в порядке», кредит не навязываем.
- **Если сломалось:** транзакции недоступны → прогноз на снапшоте с датой; истории меньше 3 мес. → радар молчит («мало данных»).
- **Откуда:** Tide Cashflow Insights, Stripe Capital [P22]; recurring streams Plaid [P16].

### K2. Предрешённый оффер в 1 клик · Must
- **Как:** сигнал → `simulate` по данным банка и снапшотам (информационную часть КИ можно без согласия [L8]) → оффер с продуктом, суммой (разрыв + буфер),
  сроком (до ожидаемого поступления) и сроком действия. «Подтвердить» создаёт обычный DRAFT; дальше полная проверка (с согласием на БКИ) — та же state machine.
- **Если итог отличается** — дифф и причина (X8). **Откуда:** Stripe Capital, Shopify Capital [P22].

### K4. Погашение из поступлений · Should
- **Как:** на оферте симуляция на данных клиента за 12 мес.: фиксированный график против «p% от поступлений + минимальный платёж за период»; стресс-тест на трёх худших месяцах.
  После выдачи — списание по договору (ГК ст. 854 п. 2 [R-12], заранее данный акцепт — ГК ст. 847).
- **Откуда:** Stripe Capital (погашение долей от продаж) [P22].

### K5. Сигнал «контракт» · Could
- **Как:** новый контракт в ЕИС, где клиент — поставщик → оффер на исполнение: доля цены минус аванс [параметр], срок — до окончания контракта плюс оплата
  (по закону до 7 раб. дней после приёмки [L13]; реальные задержки больше [M10] → буфер). Гарантия для следующих закупок (44-ФЗ ст. 96 [L14]) — рекомендация другого продукта.

## F. Работает, когда мир ломается (подробно — `07_resilience.md`, страницы F1–F2)
- **Политика факта в базе знаний:** что делать, если факт неизвестен или устарел: `STALE_OK`, `WAIT`, `ASSUME_STRICT`, `ASK`, `PROVISIONAL`, `BLOCK`, `MANUAL`, `IGNORE`.
  Fallback — часть экспертной системы, а не `try/except`: поведение продукта при отказе задаём и проверяем так же, как кредитную политику.
- **Прогресс не теряется:** каждый шаг конвейера — чекпоинт; воркер упал — шаг продолжается с последнего чекпоинта; события — через outbox [P1].
- **Честный статус:** таймлайн показывает, какой шаг ждёт какой источник и до какого срока; кабинет читает снапшоты и работает, даже когда реестры лежат.
- **Критичное — только на свежих данных:** подпись и выдача не проходят на устаревших МЧД, ЕГРЮЛ, юр. проверках (`BLOCK`).
- **Деньги ровно один раз:** ключ идемпотентности + сверка статуса в АБС перед повтором [P3] (F2).
- **Любой отказ — на лету:** песочница ставит в WireMock стаб отказа с приоритетом выше штатного, для всех ИНН или одной компании, на N вызовов или M минут;
  без перезапуска контейнеров [P18]. Пауза воркера моделирует наш собственный сбой.

## G. Нужный человек делает нужное

### U7. Задачи по вычисленным правам · Must
- **Как:** получатели — из X3: `sign` → лица с правом подписи; согласие участника → участники; поручительство → поручитель; `prepare` → все с `prepare`.
  У задачи: что, **почему именно вы** (сущность + норма), срок, что будет, если не сделать. Единый inbox по всем компаниям (R8). Только in-app.
- **SLA:** у каждого ожидания таймер → напоминание в inbox → истечение по правилам state machine.

### B4. Четыре глаза на ручные исключения · Should
- **Как:** аналитик меняет исход движка (одобряет вопреки правилу или сверх своих полномочий) → решение не вступает в силу, пока его не подтвердит второй аналитик.
  Оба действия в аудите. **Откуда:** maker-checker, принцип четырёх глаз [P14].

## H. Банку дешевле и безопаснее

### B2. Сквозная обработка (STP) · Must
Простые заявки решаются без людей; в ручную очередь попадают только исключения (выше полномочий, пограничный риск, расхождение данных, недоступный источник).
Очередь сортируется по сроку SLA и сумме. Метрика — доля заявок без ручного касания.

### B1. Досье на одном экране · Must (базовое) / Should (расширенное)
Базовое досье — часть Must-экрана кредитного специалиста: факты, трасса, исход, кнопки решения. Расширенное — всё по заявке: факты с происхождением, «что изменилось с прошлого просмотра», трасса правил, вклад факторов риска, версия политики, история событий реестров.
Досье даёт аналитику входы для профессионального суждения о финансовом положении заёмщика и качестве обслуживания долга по 590-П (п. 3.1, 3.3, 3.7 [L21] 🟡) —
сами резервы вне MVP.

### B5. Политика как код · Could
Версии политики неизменяемы, номер версии — в каждом решении. Новую версию сначала прогоняем на синтетическом портфеле (доля одобрений, средний лимит, доля ручных и контрпредложений),
потом включаем; champion/challenger — детерминированное разбиение по хэшу ИНН [P15].

### Аудит с хэш-цепочкой · Should
Журнал только на добавление; каждая запись содержит хэш предыдущей — подмену видно сразу [P19]. Решения, переходы, действия песочницы (с пометкой `sandbox`).
